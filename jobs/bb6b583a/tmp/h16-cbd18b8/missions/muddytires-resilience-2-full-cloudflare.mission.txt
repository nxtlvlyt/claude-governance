- DATA: MySQL/MariaDB on the Synology. Tables seen in pois.php: the POI nodes (`b`, with lat/lng/node_type/name/note/amenities/photo/contributor + a `meta_json` column queried via JSON_VALUE for crown_camping.legal_status / casino.overnight_rv / overnight.status), `spot_photos` (spot_id, photo), `community_review` (rating, body, photo, contributor, created_at). → MAP TO **Cloudflare D1** (SQLite): MySQL `JSON_VALUE(meta_json,'$.x')` → SQLite `json_extract(meta_json,'$.x')`; prepared statements port directly.
- AI ORACLE (oracle.php): model-agnostic NL layer — calls Anthropic `/v1/messages` (env ORACLE_MODEL default claude-haiku-4-5) with a deterministic fallback. The Synology needed a Python/curl bridge for HTTPS; **Workers call Anthropic natively** — the port is SIMPLER. NOT a vector/Qdrant system (earlier assumption was wrong).
- ENDPOINTS to port (PHP → Workers/Pages Functions, by size/effort): pois.php (9.9KB, the GeoJSON data API — DO FIRST), feed.php (8.4KB), contribute.php (9.6KB) + contribute_submit/ocr/voice, community_edit.php (5.8KB), review.php (2.3KB), search.php (2.3KB), planner.php (5.3KB), oracle.php (18KB, the Claude layer), subscribe.php (2.3KB). Static pages (landing/guides/partners/about) can stay static or become simple routes.
- SECRETS: ANTHROPIC_API_KEY (+ AIML/QDRANT names seen but oracle uses Anthropic), MODERATOR_PIN → Cloudflare Workers secrets (NOT in the repo).

STAGED PLAN (each stage its own mission, receipted; decompose under the Hajj mission-architecture):
1. **Export the live data off the NAS** (the one NAS-dependent step): mysqldump the muddytires DB (nodes + spot_photos + community_review) to a .sql/CSV. If the NAS is reachable, do this FIRST + commit the dump to a private repo (it is the irreplaceable thing). If the NAS is down, Stage 1 falls back to the pois.json snapshot (POIs only — loses review/photo history).
   FINDING 2026-06-15 (verified): the DB connection config is NOT in the backed-up muddytires-backend code — pois.php uses a shared `$db` from an include that lived ON the NAS (un-backed-up). So Stage 1 must FIRST SSH into the NAS (creds in memory reference_nas_access), LOCATE the db bootstrap/config to get the DB name + user/pass, THEN read-only mysqldump. This is a careful NAS read-operation against the operator's most-protected asset — do it in a FRESH, oriented instance with NAS access READ-ONLY, never in a drifted context.
2. **Load into Cloudflare D1**: create the D1 database, port the schema (MySQL→SQLite), import the data.
3. **Port pois.php → a Worker** querying D1, returning the same GeoJSON shape (the frontend already calls pois.json?...; point it at the Worker route). PROVE the map renders from D1.
4. **Port the write + read endpoints** (contribute / community_edit / review / search / feed / planner) → Workers on D1, secrets wired. Re-enable the interactive features.
5. **Port oracle.php → a Worker** calling Anthropic directly (drop the Synology Python bridge).
6. **Wire the frontend** (index.html) routes from the dead .php paths to the Worker routes; remove the static-only limitation.
7. **Verify**: every feature works on muddytires.ca with the home-stack tunnel OFF; the apex already points at Pages (done).

Amanah: this is the real "SOTA / NAS-proof" build. Receipts per stage (D1 query returns rows; the map renders from D1; a test contribution writes + reads back; the oracle answers). NO stage claims done without a live receipt.
