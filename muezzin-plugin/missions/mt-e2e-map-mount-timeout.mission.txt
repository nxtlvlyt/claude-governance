MAQSAD (the end): make the e2e overlap sweep's map-mount wait tolerant of van
Starlink so a slow-but-working map stops false-failing the five-guard deploy gate.
The overlap sweep opens map.html in a fresh context per cell and does
`await page.waitForSelector('#map.leaflet-container', { timeout: 30000 })`
(scripts/e2e-runner.mjs line ~606). Over Starlink, Leaflet's init routinely exceeds
30s — the author documented this in the same function (lines ~598-604, QUEUE ITEM 24,
2026-07-14: "three DETECTOR_ERROR 'Timeout 30000ms' receipts over Starlink, identical
on unchanged production"). When the wait times out, the catch at line ~808 pushes a
`DETECTOR_ERROR: ...` string into `violations`, and the cell verdict
(`ok: violations.length === 0 && ...`, line ~822) hard-fails. Because the verdict cannot
tell a MEASUREMENT timeout from a real geometric overlap, a network-timing artifact
false-REDs the deploy gate for EVERY mission — whichever cell happens to exceed 30s that
run (non-deterministic; observed on desktop/default cold and desktop/plan warm the same
day). This blocked the mt-levels deploy and forced mt-lh-boot-cpu to re-fish for a green.

THE FIX (pin these literals — do NOT choose your own value): introduce ONE module-level
constant and apply it to the `#map.leaflet-container` mount-wait ONLY.
  const MAP_MOUNT_TIMEOUT_MS = Number(process.env.MT_E2E_MAP_TIMEOUT_MS) || 60000;
Default EXACTLY 60000 (ms). Env var name EXACTLY MT_E2E_MAP_TIMEOUT_MS. Apply it to the
`page.waitForSelector('#map.leaflet-container', { timeout: ... })` call, replacing its
literal `30000`. This lets an operator raise the ceiling (90000/120000) on a slow link
WITHOUT a code change, while a broken map that never mounts within the generous window
STILL fails loudly — the author's deliberate "never silently passes" semantics (line ~604)
are preserved, not softened.

SCOPE FENCE (D13, do NOT exceed): change ONLY the `#map.leaflet-container` waitForSelector
timeout. Do NOT touch the `page.goto(..., { waitUntil: 'domcontentloaded', timeout: 30000 })`
on the line above — domcontentloaded is a fast DOM-parse wait; 30s is correct there and a
page that cannot parse DOM in 30s is genuinely dead. Do NOT touch the plan-mode-entry
DETECTOR_ERROR (line ~687, "failed to enter plan mode") — that is Class A, a SEPARATE
plan-engage race owned by QUEUE ITEM 36; this mission is Class B (map mount) only. Do NOT
reclassify DETECTOR_ERROR as inconclusive — the loud-fail-on-broken-map behavior is
intended; only the timeout is too tight.
